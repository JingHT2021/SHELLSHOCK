# ShellShock 文件盘点与统一求解架构建议

日期：2026-09-10。本文是迁移前的历史盘点；统一工作树的当前实现见 [重构说明](refactor-notes.md) 和 [逐文件说明](module-guide.md)。原始工作区保留不变。

## 1. 范围与结论

实际目录是项目根目录下并列的 `shellshock_detector/`、`shellshock_detector_yolo/`，不是后者嵌套在前者内。

- `shellshock_detector` 主要是截图采集、标注格式、训练数据、风力数字识别和旧几何识别工具；仍被运行入口使用，不能整目录直接删除。
- `shellshock_detector_yolo` 主要是 YOLO 推理、场景构造、弹道求解、碰撞验证和桌面操作。它已经依赖前一个包。
- 实时与离线入口已经调用同一个 `global_solver.solve_integer_shot`，但输入场景、风力来源、炮口处理、交互、轨迹绘制没有完全统一。
- 适合合并成一个 `shellshock` 包，内部按职责分目录。数学、事件物理和 A/B/C 流水线共用，模式只表达必须经过哪些事件。
- 本次检查基于当前工作区。检索开始时 `shellshock_detector_yolo/world_geometry.py` 已有未提交修改，未覆盖。
- 附件作为设计参考阅读，其中“删除”“实现顺序”等文字不当作用户已单独授权执行的命令。

## 3. 重复与分叉的证据

### 3.1 可以直接统一的重复

统一文本换行后，两包的 `__init__.py`、`models.py`、`shot_modes.py`、`obstacle_geometry.py` 完全相同。原始字节不同，因此不能只看文件哈希断定没有重复。

两份 `wind.py` 的差异主要是数字识别器导入路径、变量名、两行解释注释；当前算法等价。先选一份实现，再让所有调用者导入同一处。

注意：两份重复模块即使内容一样，Python 导入得到的 class 对象仍是不同对象。整合要同时统一调用方与序列化入口，不能仅比较函数内容。

### 3.2 数学重复与业务区别

| 重叠 | 位置 | 处理 |
|---|---|---|
| 恒加速位置/速度 | `collision.py`、`WormholeTrajectory.position`、`ballistics.py`、绘制代码 | 一套向量公式；明确旧代码有 y 向上和屏幕 y 向下两种约定 |
| 定速弹道求解 | `ballistics._fixed_power_solutions`、`wormhole_solver.solve_ballistic_for_speed` | 抽纯数学接口，方向与 UI 限制在外层 |
| 抛物线进圆 | `collision.parabola_circle_roots`、`wormhole_solver.first_circle_entry_time`、`portal_replay._entry_time` | 共用交点根；保留“进入/离开/初始在内/切触”的不同事件策略 |
| 二次/三次/多项式根 | `collision`、`wormhole_solver`、`reflection_solver` | 统一稳定求根、降阶、实根和容差策略 |
| 二维叉积 | `collision.cross2`、`reflection_solver._cross` | 合并 |
| 炮口与角度换算 | `muzzle_geometry`、`replay.solution_launch_point`、旧关键点迁移、标注器 | 共用标定和转换；旧数据版本转换保留独立入口 |
| 反射公式与碰撞后传播 | 三个 replay 模块、`proxy_events`、`trajectory_sampling`、反射求解器 | 单一事件变换；B 可简化检查强度，不能变更物理公式 |
| 几何数据类型 | 两份 `models`、颜色识别模型、World 模型、两套标注类型 | 共用几何基元；检测置信度、标注来源、事件行为保持各自领域字段 |

`obstacle_geometry.py` 是图像中找形状；`collision.py` 是判断轨迹与形状相交。两者不应因为都叫“几何”就混在一个数学文件中。

### 3.3 已经共用的部分与尚未共用的部分

实时路径：窗口截图 → YOLO → World 构造 → 图片风力识别 → `solve_integer_shot` → 点击。

离线路径：读图片 → YOLO/人工合并 → 相同 World 构造（再应用人工覆盖）→ 元数据风力 → 相同 `solve_integer_shot` → 另一套轨迹绘制。

差异包括：

1. 实时使用鼠标目标，离线默认选敌人；离线风力默认来自元数据，缺失时为 0，没有复用实时 OCR 回退。
2. 离线 `--barrel-extension` 影响炮口反推与画线，而核心 `muzzle_position` 使用固定标定；改参数可能造成求解与画线不一致。
3. `trajectory_sampling.py` 反射分支通过有限时间探针寻找最接近反射点的位置，未直接消费精确反射时间；反射与虫洞混合路径不能由这种两段画法完整重建。
4. `portal_replay.py` 与 `combined_replay.py` 对最终目标最近距离的检查区间不同，统一前需要明确命中事件定义，不能简单删除一份。
5. 标注器拥有独立编辑状态、坐标转换和保存逻辑；离线入口也有一套。应共享交互命令和标注编辑模型。

### 3.4 当前求解不是全部暴力枚举

- 普通模式：连续解析种子，再验证少量整数邻域。
- 反射主流程：A/B/C 已存在，固定反射点非退化问题已有二次方程求时间比例；仍有表面代表点、退化情况下对数比例区间采样及候选上限。
- 虫洞模式：每条一路/两路虫洞组合上，从理论最低力度到 100（或反向）逐力度尝试，再做角度邻域验证。这是需要重点替换的搜索。
- `_legacy_solve_reflection_bundle` 还留在 `reflection_solver.py`；本次自有源码引用检索只找到定义，没有发现入口调用。不能把旧函数里的全力度循环误认为当前反射主流程。
- 反射 C 当前虽然构造 angle±1、power±3 邻域，却每个连续样本只保留其中 grid_error 最小的一项。后续应按预算保留有意义的邻域，而非以“最近取整”替代整数可行性验证。

## 4. 黑洞、虫洞、奖励需要明确分开

类别表已定义 `7 blackhole`、`8 double_damage`、`9 Triple_damage`。但 World 当前只有圆反射物、线反射物、配对虫洞与己方位置；7/8/9 没有对应物理字段，也没有伤害奖励排序。

建议解释用户需求为：

- 黑洞（7）：暂时是禁止经过的圆形区域。不模拟引力，不作为 B 层必须穿越的候选途径点。
- 虫洞（5/6）：进出口平移，速度保持；沿用当前代码保留相对入口偏移的语义。
- 二倍/三倍奖励（8/9）：可穿越的触发区域；位置、速度都不改变，只记录奖励事件。

“无位移的黑洞”在需求中更适合实现为“无位移的圆形触发事件”。这样它与虫洞共用圆进入判定，又不会与禁止进入的黑洞混淆。

黑洞不能直接追加到当前 `World.circles`：现有反射算法会把 circles 当反射面。形状与事件行为必须分开。

奖励在所有可行解中优先：先满足命中、禁区和当前模式的硬约束，再比较奖励等级，再比较误差、间隙与力度/高低弧。不能让穿过三倍圈但没有命中的解胜出。

单次奖励优先级明确为 3 > 2 > 无。连续取得多个奖励是否相乘、覆盖、同一个奖励能否重复触发，用户未说明，不能直接假定 2×3=6。将累积规则做成独立配置，保存经过的奖励 ID；在确认前不宣称支持真实叠加规则。

## 5. 推荐目录与共用边界

建议用 `math2d` 命名数学目录，避免与 Python 标准库 `math` 混淆。反射、虫洞、黑洞等目录只保存事件规则和专用候选策略，不各复制 A/B/C。

```text
shellshock/
  domain/                 # 场景、几何、类别、事件路线、解、轨迹段
  math2d/                 # 无图像/窗口依赖
    vectors.py
    frames.py
    roots.py
    ballistics.py
    intersections.py
    distances.py
  physics/
    calibration.py        # 重力、风、速度/力度和尺寸标定
    launch.py             # 同一炮口模型
    engine.py             # 唯一精确事件传播/验证引擎
    events/
      reflection/         # 线/圆反射法线与变换
      portal/             # 入口、出口、平移、再入规则
      blackhole/          # 当前仅 forbidden_region
      reward/             # 二倍/三倍触发与奖励累计策略
  planning/
    routes.py             # 事件顺序与路线约束
    policies.py           # 普通/必须反射/必须传送、高低弧、奖励排序
    layer_a/              # 连续可达域必要性判断
    layer_b/              # 非反射三点种子、反射连续解与廉价检查
    layer_c/              # 整数邻域、真实事件复验
  perception/             # YOLO、风力、颜色几何、场景构造
  annotations/            # 标注读写、合并、人工覆盖
  interaction/            # 统一编辑状态、选目标/模式/候选、坐标映射
  application/            # analyze_frame、solve_scene、recompute、报告
  adapters/               # Windows 窗口输入、文件图片输入、点击输出
  capture/                # 截图与元数据存储
  rendering/              # 只画已经验证的轨迹段，不重做事件求解
  datasets/               # 训练集准备与格式转换
  evaluation/             # Pose 误差、截图回归、性能对比
  config/                 # 项目路径、模型、搜索预算
```

三个根入口名称保持可用，内部只组装适配器。公共数据流为：

```text
WindowFrame / FileFrame
    → analyze_frame(frame, metadata, manual_overrides, config)
    → SceneSnapshot + SolveRequest
    → RoutePolicy → Layer A → Layer B → Layer C
    → SolveResult（真实发射点、整数操作量、事件记录、TrajectorySegments）
    → 统一绘图/报告/候选管理
```

Windows 屏幕坐标先转客户区像素；离线显示坐标通过带黑边视口逆变换回原图像素。求解器只接受原图像素场景。

风力来源顺序建议为人工覆盖 > 已存可信元数据 > 图片识别；缺失状态明确记录，由调用配置决定能否假设零风。相同 Frame、Scene、SolveRequest 和配置必须产生相同解。

每个轨迹段记录起点、初速度、加速度、时长和起止事件。传送是位置跳变，绘图不能把入口出口连成一段飞行线。手动调整角度/力度也调用相同引擎，仅允许返回未命中目标的预览结果。

模式定义建议：普通模式默认无反射/无传送；反射模式至少一次反射，可带传送；虫洞模式至少一次传送，可带反射。首版可保留现有一次反射、两次传送的规模限制，写入请求配置，避免误称支持任意复杂路径。

## 6. A/B/C 数学设计及计划书修正点

### 6.1 合加速度建系

在现有屏幕坐标（y 向下）中统一 a=(风加速度, 重力加速度)，用正交变换使局部 a=(0,-g)，g=|a|。所有自由飞行段复用：

```text
p(t) = p0 + v0*t + 0.5*a*t²
v(t) = v0 + a*t
```

已有 `acceleration_aligned_frame` 可作为起点。恒加速度非退化段是抛物线；初速度平行加速度时轨迹退化为直线，a=0 时为匀速直线，需要显式处理。遇反射/传送后继续同一恒加速度模型，但整条路线是多段曲线加事件跳变，不是一条全局抛物线。

### 6.2 A：连续时间必要性筛选

采纳计划书中的传播方向：到达速度集合与事件变换共用，排除确实不存在正飞行时间的路线；删除象限允许表与离散速度符号组。

但不能每到一个节点重新放开为独立的 `d/t + a*t/2` 全集，必须保留上游已施加的速度和时间关联。否则不是整条链传播，只是互不相干的逐段检查。采用外包集合时可以放宽，但只能增加假阳性，不能误删。

对于固定的普通三点 O→W→T，令 d1=W-O、d2=T-W、r=t2/t1>0，则：

```text
d2 = r*d1 + 0.5*a*t1²*r*(1+r)
```

在 a=(0,-g) 坐标中，若 d1.x≠0：

```text
r = d2.x/d1.x
t1² = 2*(d2.y-r*d1.y) / (-g*r*(1+r))
```

只有 r>0 且 t1²>0 才有该非退化固定三点解。这是完整方程推导出的判据，不是旧象限表。d1.x≈0、零加速度、共线、重合等情况走独立退化分支，不用一个小阈值直接否定。

对固定反射点 R 与固定速度变换矩阵 M，令 d1=R-O、d2=T-R：

```text
d2-r*M*d1 = 0.5*t1²*(r*M*a+r²*a)
cross(d2-r*M*d1, M*a+r*a) = 0
```

后式通常是 r 的至多二次方程。求正根、恢复正时间并验原方程即可；退化分支单独处理。已有 `fixed_contact_solutions` 含类似可复用推导，但夹杂角度、最大时间、入射阈值等 B/C 限制，不能原样作为 A 层判据。

多事件链需保留共享参数约束，可用解析消元、单调区间或保守区间外包逐步收缩。低维求根失败或优化未收敛不能当“不可能证明”。对不能证明排除的路线返回 PASS 并标记尚未收紧的范围。

A 不应以中心/四点/八点全部失败证明整个圆区域不可达。中心与四点适合作 B 种子；A 要用区域外包或证明覆盖的参数区间。当前反射 A 对直线只取 0/0.5/1、圆只取少量代表点，需要一起处理这种覆盖风险。

### 6.3 反射公式存在实质冲突

附件要求：`M(v)=2*(v·n)*n-v`，即关于法线轴对称。

现有反射求解、精确复验、绘制采用：`M(v)=v-2*(v·n)*n`，即翻转法向分量、保留切向分量。两者互为负号。

例：水平板、n=(0,1)、入射 v=(3,4)。现有公式得到 (3,-4)，附件公式得到 (-3,4)。后一结果继续沿原来的竖直方向运动。仅把 n 换成 -n 不会消除差别。

因此本次只记录冲突，不替换。建议先保留当前反射行为，用已知截图/实测轨迹确认究竟是板面法线定义不同，还是确实要更改规则。一经确认，A/B/C/手动预览必须共用同一个事件变换。

### 6.4 B：少量连续种子和低维求解

无反射路径：从奖励/虫洞入口区域中心、上下左右各一点生成候选（通常共五点，偏移量由有效触发半径控制），利用普通三点解析关系求时间、初速度、角度与力度。点在边界附近时留适当余量，避免只能擦边。

含虫洞时先按已走过的位移把途径点与目标展开到同一个虚拟坐标系；不能只平移最终目标、却把中途关键点留在原位置。种子生成后仍需验证每个入口按计划顺序触发。

一条弹道通过固定起点、一个途径点、目标，在非退化条件下能确定候选；多个任意指定途径点一般形成过约束，不能承诺每个组合都能精确经过。可用一个途径点生成解，检查其他区域，必要时只在失败区域对应的低维参数上细化。

有反射路径：复用固定接触点解析解，在线段参数或圆弧参数上进行有界分支求根/优化。圆的法线依赖接触点，必须一起更新。

五点种子是低成本候选方法，不保证找到所有可行解。若种子失败，可对有希望的触发区域做自适应参数区间细化；不能悄悄退回全力度×全角度枚举。预算耗尽应报告“未找到可验证解/预算耗尽”，而非声称已证明不可达。

B 承担力度/角度合法性、分支稳定性、廉价事件顺序和明显禁区检查；必须在候选截断前保留最高奖励级别的路线，不能只在最终结果才加奖励分数。

### 6.5 C：整数控制与唯一事件复验

把连续候选转成小范围整数邻域；角度取整会改变炮口位置，要按整数角度重新建立真实发射点再验证。去重键至少包括方向、角度、力度及所需路线语义，不能只用 angle/power 混淆左右发射。

精确事件引擎负责最早的圆/线段相交、传送、反射、奖励、黑洞和目标事件。统一零时间、自身刚离开表面、虫洞出口初始在内、同时事件和切触策略。

明确目标是进入接受区域还是到达最近点，并对所有模式保持一致。黑洞起点在内以及边界相切是否拒绝也要统一；按“不可经过”建议包含边界拒绝，并将额外安全余量与真实半径分开。

小范围整数验证是必要的离散检查，与全局暴力搜索不同。最终返回真实通过的奖励、完整事件顺序、轨迹段、命中误差与失败原因。

## 7. 路径合并与迁移顺序

### 7.1 路径集中管理

统一 `config/paths.py` 或等价配置入口，集中项目根、YOLO 权重、数字模型、截图、人工标注、复验输出与日志路径。

当前多数入口用 `Path('train/...')`，依赖启动时的工作目录；数字识别器却用 `Path(__file__).resolve().parents[1]`。一旦移动到更深的包内，后一种写法也会找错根。迁移时应统一固定项目根定位/显式配置，保留 CLI 覆盖，并明确相对 CLI 路径以哪个目录解析。

需要同步更新：两个旧包的绝对/相对 imports、根入口脚本、训练/评估脚本、默认权重、运行脚本、README、数据集 YAML 和元数据内确实引用旧位置的字段。若数据不移动，不应无差别改写历史标签/元数据。

离线 `_paths` 当前固定找 `train/annotate`，即使输入来自 `train/yolo_captures/full`。应以 CaptureBundle 统一定位图片、标签、几何、风力和元数据，优先同一数据包，另行提供跨目录兼容策略。

### 7.2 三种整合路线

| 方案 | 优点 | 代价/问题 |
|---|---|---|
| 只把旧包并进 YOLO 包 | 改动小 | 巨型文件和重放分叉仍在，不满足后续共享计算目标 |
| 单包分职责、分阶段迁移（推荐） | 可核对行为等价，能复用已验证数学 | 需维护一次完整 import/路径映射 |
| 一次全部重写 | 布局自由 | 同时改变输入、物理、搜索、UI，很难定位回归来源 |

推荐执行阶段：

1. 固定若干真实截图及对应 SceneSnapshot、风力、目标、模式、配置和输出，建立回归基准。
2. 单包合并、确定性重复去重、集中路径与类别；保持原求解行为，入口同步改 imports。项目内旧包引用清零后删除旧实现；若确有外部调用需要，临时兼容层只 re-export，不能保留第二份算法。
3. 抽取公共数学、领域类型、发射模型；合并事件引擎，绘图只消费轨迹段；实时/离线/标注编辑接同一服务。
4. 增加黑洞禁区、奖励事件及可行解奖励优先排序；完整贯通识别→World→候选→验证→显示。
5. 用连续参数 A、三点/反射 B、局部整数 C 替换旧符号筛选与虫洞力度扫描；将模式改为事件要求。
6. 对比截图回归、性能和失败原因，更新使用文档，清理经引用检查确认无调用的旧实现。

这是建议顺序，并非本次已经完成的迁移。

## 8. 后续验收标准

- 同一帧/场景/目标/风力/配置经实时适配器与离线适配器进入核心后，候选、整数解、事件顺序、轨迹段相同；Windows 点击仅在输出适配器内。
- 修改人工圆/线/风力后，三入口共用同一重算函数与物理配置。
- 数学层无 OpenCV、YOLO、Windows、训练数据依赖；坐标正逆变换有往返校验。
- 用从已知真实可行轨迹反向构造的路径检查 A 不误删；覆盖有风、退化直线、切触、圆区域边缘、反射前后虫洞。
- 相交判定覆盖最早根、线段端点、圆切触、初始在圆内和事件同时发生。
- 黑洞各模式都不可穿越，奖励各模式都参与候选和最终排序；有奖励但不命中的解不胜出。
- 统一引擎输出与画线一致，虫洞跳跃不被画成飞行线。
- 统计 A 路线数量、B 求根次数、C 整数验证次数、耗时；主路径不再含全力度扫描。
- 数据迁移前后图片/标签数量和配对关系不变；从其他工作目录启动也能找到配置中的权重与数据。

本次已完成源文件清单、文本/AST 重复比较、主调用链及路径检索；没有运行游戏窗口、执行点击、训练模型或修改物理代码。上述数学方案是基于方程的设计推导，尚未以代码和截图验证。不能把本报告作为求解准确率或运行性能已经通过的证明。
